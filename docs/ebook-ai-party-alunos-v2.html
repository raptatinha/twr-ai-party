The 4Ds + Modelos + Contexto

Fundação15 + 15 min
The 4Ds
  • Delegation: saber quais tarefas delegar e escolher o modelo adequado para cada tipo de tarefa (ex: Cloud 4.6 Opus High para raciocínio complexo, Sonnet para tarefas mais leves)
  • Description: fornecer descrições claras com exemplos, arquivos e regras. O tamanho do contexto impacta diretamente o consumo de tokens
  • Discernment: avaliar criticamente, validar com colegas, consultar documentação oficial. Não confiar cegamente nas respostas
  • Diligence: usar variáveis de ambiente, evitar dados sensíveis, ser transparente sobre uso de IA em documentos e tickets (ex: marcar no Jira)
Escolha de modelos
  • Cada modelo e treinado com foco diferente (código, dados, linguagem natural)
  • O mesmo prompt gera resultados diferentes entre modelos
  • Leia a documentação do modelo antes de julgar se e bom ou ruim
  • Compare modelo A vs modelo B para a mesma tarefa
Context management
  • Conversa longa sem higiene reduz qualidade da IA
  • Use /compact para preservar contexto essencial
  • Use /clear para iniciar tarefa totalmente nova
  • Trate tokens como limite de foco e memória de trabalho
  • Salve informações importantes em arquivos para evitar alucinações e desperdício de tokens
Assistentes comparados
  • Cursor: IDE com Rules/Skills, suporta multiplos modelos
  • Claude Code: refatoração e leitura de base legada
  • GitHub Copilot: autocompletar e sugestões inline
  • Codex: tarefas de codificação autônomas
  • Gemini: alternativa multi-modal
Para lembrar

Boas respostas não comecam no prompt final. Elas comecam no gerenciamento de contexto ao longo da sessão e na escolha do modelo certo para a tarefa.

MCP + Playwright MCP

Integração10 + 25 min
MCP em uma frase
  • Padrão que conecta IA a ferramentas e dados externos
  • Permite ação real, não só texto gerado
  • Cria fluxo auditavel entre pedido e execução
Integrações demonstradas
  • Jira: criação de tickets e comentários automáticos
  • Slack: notificações para times responsaveis
  • Playwright: automação de browser via MCP
  • Figma: análise de design
Playwright MCP — como funciona
  • Servidor MCP que dá ao LLM ferramentas de automação de browser
  • Opera via accessibility snapshots — não precisa de vision model
  • LLM lê a árvore de acessibilidade, identifica refs (ex: ref=e5) e executa ações
  • Ferramentas disponíveis: navegar, clicar, preencher, screenshot, tabs, network mocking
  • browser_run_code: permite executar scripts Playwright completos quando necessário
  • Storage state: salvar/restaurar cookies e localStorage entre sessões
  • Modos: headed (padrão), headless, persistent, isolated, browser extension
MCP vs CLI vs Agents — comparativo real
  • Playwright MCP: servidor de protocolo para IDEs (Cursor, VS Code, Claude Desktop). Ideal para loops iterativos e exploração. Alto consumo de tokens por snapshot
  • playwright-cli: CLI otimizada para coding agents (Claude Code, Copilot). Comandos concisos, token-eficiente, com skills instaláveis
  • Playwright Test Agents: pipeline de 3 agentes (Planner → Generator → Healer) que geram suítes de teste completas a partir de um seed test
  • MCP e CLI controlam o mesmo browser — a escolha depende do ambiente (IDE vs terminal)
Configuração MCP (Cursor / VS Code / Claude Desktop):
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}

Accessibility snapshot retornado pelo MCP:
- heading "todos" [level=1]
- textbox "What needs to be done?" [ref=e5]
- listitem:
  - checkbox "Toggle Todo" [ref=e10]
  - text: "Buy groceries"

O LLM usa refs para interagir:
→ ref=e5 para digitar no campo
→ ref=e10 para marcar o checkbox

Opções de configuração do servidor:
--headless          sem janela visível
--browser=firefox   escolher browser (chrome, firefox, webkit, msedge)
--isolated          cada sessão começa limpa
--port 8931         modo servidor HTTP standalone
--extension         conectar ao browser existente

Playwright CLI + Agents

Hands-on25 + 15 min
playwright-cli — CLI para coding agents
  • Ferramenta de linha de comando projetada para coding agents (Claude Code, GitHub Copilot, etc.)
  • Comandos concisos e token-eficientes — não carrega schemas grandes no contexto
  • Após cada comando, retorna snapshot da página com refs para interação
  • Sessões persistentes — cookies e estado preservados entre chamadas
  • Skills instaláveis: playwright-cli install --skills
  • Sessões nomeadas: playwright-cli -s=login open https://app.com
  • Dashboard visual: playwright-cli show para monitorar sessões ativas
Playwright Test Agents: Planner → Generator → Healer
  • Pipeline de 3 agentes que geram suítes de teste automaticamente
  • 🎭 Planner: explora a app navegando ao vivo, gera plano de teste em Markdown (specs/). Recebe seed test como ponto de partida
  • 🎭 Generator: lê o plano Markdown e gera testes Playwright em tests/. Verifica seletores e assertions ao vivo
  • 🎭 Healer: executa testes que falharam, inspeciona a UI atual, propõe patches. Guardrails impedem loop infinito
  • Setup: npx playwright init-agents --loop=vscode (ou --loop=claude)
  • Healer tende a corrigir o teste, não a encontrar bugs da aplicação
# playwright-cli — comandos essenciais
npm install -g @playwright/cli@latest

playwright-cli open https://exemplo.com --headed
playwright-cli snapshot                    # ver estado da página
playwright-cli click e15                   # clicar usando ref
playwright-cli fill e5 "teste@email.com"   # preencher campo
playwright-cli type "texto livre"          # digitar texto
playwright-cli press Enter                 # pressionar tecla
playwright-cli screenshot                  # capturar tela
playwright-cli network                     # ver requisições
playwright-cli console                     # ver console do browser
playwright-cli eval "document.title"       # executar JS

# Sessões e monitoramento
playwright-cli -s=checkout open https://loja.com
playwright-cli list                        # listar sessões
playwright-cli show                        # dashboard visual

# Playwright Test Agents — setup
npx playwright init-agents --loop=vscode
# Estrutura gerada:
# specs/    → planos em Markdown (Planner)
# tests/    → testes gerados (Generator)
# seed.spec.ts → ponto de partida
Para práticar em casa
  • Instale playwright-cli e explore 1 fluxo da sua app com open + snapshot + click
  • Rode npx playwright init-agents e use o Planner para gerar um plano de teste
  • Revise o plano gerado em specs/ antes de rodar o Generator
  • Compare o código gerado pelo Generator com seus testes existentes

Cursor: Rules, Skills e Agents

Produtividade25 min [DEEP]
Cursor Rules
  • Carregadas automáticamente conforme tipo de arquivo
  • Padronizam comportamento do assistente
  • Definem convenções de teste, fixtures, autenticação
  • Reduzem retrabalho em PR review
  • Garantem consistência de output entre pessoas do time
Cursor Skills
  • Conjuntos de instruções executadas sob demanda
  • Transferem conhecimento humano para arquivos reutilizáveis
  • Podem ser criadas a partir de exemplos, prompts ou do zero
  • Evoluem conforme necessidades do projeto
  • Podem ser globais ou por contexto específico
Agents no Cursor
  • Entidades executoras que acionam skills e rules
  • Gerenciam checkout/check-in de skills sob demanda
  • Carregam apenas o necessário, reduzindo consumo de tokens
  • Sobreposição de conceitos com skills/rules é normal
Diferenca-chave
  • Rules: automática por contexto (tipo de arquivo)
  • Skills: acionada sob demanda pelo usuario
  • Agents: executores que combinam ambos
  • Não se apegue a nomenclaturas — foque no resultado
Para práticar em casa
  • Crie 1 rule para padronizar formato de testes no seu projeto
  • Crie 1 skill para uma tarefa recorrente (ex: revisão de código, análise de log)
  • Compare resultado do assistente com e sem rules ativas
  • Compartilhe sua skill com um colega e peça feedback

Skills na prática: Dashboards e Observabilidade

Casó real10 min
Casó real: ClickHouse + Grafana
  • Skills acessam ClickHouse para executar queries automáticas
  • Geram dashboards em JSON e publicam via API no Grafana
  • Antes: semanas para criar dashboards manualmente
  • Agora: horas com automação via skills + scripts Python
  • Skills criadas sob demanda com prompts simples no chat
Framework honeydoo (wrapper Playwright)
  • Coleta dados antes, durante e após execução de testes
  • Armazena em múltiplas tabelas no ClickHouse
  • Integrações automáticas com CircleCI
  • Notificações automáticas via Slack para times responsaveis
  • Abertura automática de tickets no Jira em caso de falha
Fluxo de dados:
Testes (honeydoo/Playwright)
  -> Coleta métricas (antes/durante/depois)
  -> ClickHouse (armazenamento otimizado)
  -> Skills (queries automáticas sob demanda)
  -> Grafana (dashboards via API)
  -> Slack/Jira (notificações e tickets)

Exemplos de dashboards gerados:
- Monitoramento de runs de testes
- Taxa de falhas com alertas por threshold
- Tempo de execução por suite
- Identificação de falhas recorrentes
- Diagramas de entidades do banco
Para lembrar

A extração de dados e feita pelo framework (honeydoo), não pela IA. A IA entra na camada de consulta e visualização, gerando queries e dashboards via skills.

Cultura de IA e Boas Práticas

Mindset15 min
Adoção de IA na empresa
  • Autonomia dos times para criar skills e pipelines próprios
  • Cotas para ferramentas como Cursor e Claude Code
  • Incubadora interna para projetos inovadores
  • Skills criadas para um time rápidamente adaptadas por outros
  • Repositório centralizado para compartilhamento de projetos e skills
Produtividade e qualidade
  • Aumento percebido de produtividade, mas sem métricas precisas ainda
  • Experimentação constante dificulta estabelecer baseline
  • Foco atual: qualidade dos resultados, não velocidade pura
  • Mensuração pode vir em fases futuras com processos mais estáveis
Boas práticas consolidadas
  • Revisão humana: revise planos, skills e testes gerados pela IA. Não confie cegamente
  • Tokens como recurso: use arquivos intermediários, compactação de contexto, carregue apenas skills necessárias
  • Arquitetura primeiro: mantenha POM, separação de responsabilidades e padrões consistentes
  • Evolução contínua: cenário muda rápido — experimente, adapte e compartilhe
Segurança e transparência (Diligence)
  • Nunca compartilhe dados sensíveis com a IA
  • Use variáveis de ambiente para credenciais
  • Marque em tickets e documentos quando IA foi usada
  • Valide fontes antes de confiar em respostas geradas
Regra de ouro

IA não substitui boa arquitetura de testes. Sem governança, velocidade sobe, mas qualidade cai. Ferramenta boa é a que resolve seu problema com qualidade e responsabilidade.
